# Data model

Each writer keeps two databases:
- **`waypoint.db`**: the Turso Sync replica, pushed to and pulled from the cloud DB. The schema below is for this database unless stated otherwise.
- **`queue.db`**: local only, never synced. Described in [write-path-and-sync.md](write-path-and-sync.md#queue).

Conventions:
- Timestamps are `INTEGER` Unix milliseconds.
- JSON columns are `TEXT` holding a JSON object.
- ID columns use the default `BINARY` collation, never `NOCASE`.
- **`PRAGMA foreign_keys` is OFF on `waypoint.db`.** Rows pulled from other writers may arrive in any order, so the `REFERENCES` clauses are documentation only. The committer enforces the invariants instead. Spike S1 confirmed that pulls bypass FK enforcement even with the pragma on: a child row was applied before its parent existed ([Turso Sync notes](turso-sync-notes.md#sync-semantics-s1)).
- A share link may be created while its collection or pinned revision is still queued. Its row can precede the target row in `waypoint.db` and the cloud. The reader joins to the target and returns 404 until the target is present; purging the queued collection removes the link.

## IDs

### Primary keys: TypeID

Format: `<3-letter prefix>_<26 lowercase Crockford base32 chars>`, where the body is a UUIDv7. IDs sort by creation time and are always 30 characters long. They are generated with `typeid-js`.

| Prefix | Entity | Generated by |
|---|---|---|
| `col_` | collection | client (the MCP server or API caller); the writer generates one if absent |
| `rev_` | revision | client; the writer generates one if absent |
| `shl_` | share link (phase 2) | writer |
| `grt_` | grant (future) | writer |
| `aud_` | audience (future) | writer |
| `cmt_` | comment (future) | writer |

- **No environment segment.** Environments are kept apart by separate databases and the [environment guard](write-path-and-sync.md#environment-guard).
- **Blobs use a natural key:** `sha256:<64 lowercase hex>`.
- **Keyless tables.** Tables keyed by another entity or by a composite natural key (`collection_tombstones`, `revision_files`, `renditions`) have no ID of their own.
- **Prefix checks.** Each table enforces its prefix, e.g. `CHECK (id GLOB 'rev_*' AND length(id) = 30)`.

### Public IDs

`public_id = lowercase_crockford_base32(sha256(id))[0:12]`, giving 60 bits.

- **Derived, not random.** The same ID always yields the same public ID. A retried write committed by two writers produces byte-identical rows, so last-push-wins resolves them harmlessly, and URLs already handed out never change.
- **Revision public IDs are globally unique,** so a URL can name a revision without its collection (`/raw/r/<id>/…`).
- **`UNIQUE(public_id)` on both tables.** At 10⁵ entities the collision probability is about 10⁻⁹.
- **Golden vector:** `publicIdFor('col_01j9qz7x2bm4d8vk3np6rt9hcs') = 'apwyysc2zcj6'`. The derivation must never change, because URLs depend on it.
- **Never API input.** Agents and the API use IDs, and every response also includes URLs. `resolve_url` maps a URL back to IDs.
- **Lowercased at the router boundary.**

### Minting and validating client-generated IDs

**Minting:** whoever mints a revision ID uses the timestamp `max(now, parent_timestamp + 1 ms)`. That ID always sorts after its parent, even if this machine's clock is behind the machine that created the parent.

**Validation:** the writer rejects a client-supplied `col_` or `rev_` ID unless:
- It parses as a TypeID with the right prefix and a UUIDv7 body.
- Its timestamp is no more than 5 minutes in the future (otherwise `clock_skew`) and no more than 7 days in the past (otherwise `stale_id`). The client should mint a new ID rather than retry.
- For revisions, it sorts after `parent_revision_id`. Otherwise the error is `id_before_parent`, with `details.parent_timestamp`, so the client can mint again using the rule above.

**Idempotency:** retries with the same IDs are safe.
- `create_collection` with a `collection_id` that already exists, and a `revision_id` that is that collection's first revision, returns the existing collection and revision.
- `add_revision` with a `revision_id` that already exists in the same collection with the same parent returns the existing revision.
- Reusing an ID for a different collection or parent returns `409 revision_conflict`.

## Tables (phase 1)

```sql
CREATE TABLE meta (                        -- environment guard
  key   TEXT PRIMARY KEY,                  -- 'environment' -> 'dev' | 'prod'
  value TEXT NOT NULL
);

CREATE TABLE collections (                 -- the only mutable table (title, metadata)
  id          TEXT PRIMARY KEY CHECK (id GLOB 'col_*' AND length(id) = 30),
  public_id   TEXT NOT NULL UNIQUE,
  title       TEXT NOT NULL,
  metadata    TEXT NOT NULL DEFAULT '{}',  -- free-form: source host, project, tags...
  created_at  INTEGER NOT NULL
);

CREATE TABLE collection_tombstones (       -- soft delete; presence = deleted
  collection_id TEXT PRIMARY KEY REFERENCES collections(id),
  deleted_at    INTEGER NOT NULL,
  note          TEXT
);

CREATE TABLE revisions (                   -- insert-only
  id                 TEXT PRIMARY KEY CHECK (id GLOB 'rev_*' AND length(id) = 30),
  public_id          TEXT NOT NULL UNIQUE,
  collection_id      TEXT NOT NULL REFERENCES collections(id),
  parent_revision_id TEXT REFERENCES revisions(id),
  head_path          TEXT NOT NULL,
  message            TEXT,
  metadata           TEXT NOT NULL DEFAULT '{}',  -- source host, agent run id, ...
  created_at         INTEGER NOT NULL
);
CREATE INDEX revisions_by_collection ON revisions (collection_id, id);

CREATE TABLE revision_files (              -- insert-only; the manifest
  revision_id TEXT NOT NULL REFERENCES revisions(id),
  path        TEXT NOT NULL,
  blob_hash   TEXT NOT NULL REFERENCES blobs(hash),
  mime        TEXT NOT NULL,
  size        INTEGER NOT NULL,
  PRIMARY KEY (revision_id, path)
);
CREATE INDEX revision_files_by_blob ON revision_files (blob_hash);

CREATE TABLE blobs (                       -- insert-only, idempotent
  hash        TEXT PRIMARY KEY CHECK (hash GLOB 'sha256:*' AND length(hash) = 71),
  size        INTEGER NOT NULL,
  uploaded_at INTEGER NOT NULL             -- row exists => object is in the bucket
);

CREATE TABLE renditions (                  -- insert-only, idempotent
  source_hash      TEXT NOT NULL REFERENCES blobs(hash),
  renderer         TEXT NOT NULL,          -- e.g. 'markdown'
  renderer_version INTEGER NOT NULL,       -- 1, 2, ... (integer so MAX() orders correctly)
  output_hash      TEXT NOT NULL REFERENCES blobs(hash),
  output_mime      TEXT NOT NULL,          -- e.g. 'text/html'
  created_at       INTEGER NOT NULL,
  PRIMARY KEY (source_hash, renderer, renderer_version)
);

CREATE TABLE share_links (                 -- added in migration 0003
  id            TEXT PRIMARY KEY CHECK (id GLOB 'shl_*' AND length(id) = 30),
  token_hash    TEXT NOT NULL UNIQUE,      -- sha256:<64 lowercase hex> of the token
  collection_id TEXT NOT NULL REFERENCES collections(id),
  revision_id   TEXT REFERENCES revisions(id), -- NULL follows latest
  label         TEXT,
  expires_at    INTEGER,
  revoked_at    INTEGER,                   -- only ordinary update
  created_at    INTEGER NOT NULL
);
CREATE INDEX share_links_by_collection ON share_links (collection_id);
CREATE INDEX share_links_by_token_hash ON share_links (token_hash);

CREATE TABLE schema_migrations (
  id         TEXT PRIMARY KEY,             -- e.g. '0001_init'
  applied_at INTEGER NOT NULL
);
```

### Derived values (never stored)

- **Latest revision of a collection:** the highest `id` among its revisions that aren't failed. On a writer, this includes pending revisions from its own queue.
- **Display number `#N`:** a revision's 1-based position when its collection's revisions are ordered by `id`.
- **Collection "updated at":** the timestamp embedded in its latest revision's ID.
- **Deleted:** a tombstone row exists.
- **Rendition to serve:** `MAX(renderer_version)` for `(source_hash, renderer)`.
- **Is markdown:** `mime = 'text/markdown'`, inferred from the `.md` and `.markdown` extensions when not given. MIME types are normalized at ingest to their lowercase essence (`type/subtype`, parameters stripped), so exact comparison works.

## Invariants

1. **Blob before row.** A `blobs` row exists only once the object is in the bucket. A `revision_files` or `renditions` row is inserted only together with, or after, the `blobs` rows it references. As a result, the cloud DB never references a missing object.
2. **Insert-only.** The only `UPDATE`s allowed are to `collections.title` and `collections.metadata`, and on `share_links`, setting `revoked_at` and moving a non-null `expires_at` later (extend; D48). The only `DELETE`s allowed are undelete (removing a tombstone) and [purge](#deletion).
3. **Every revision's head path is in its manifest.**
4. **Paths** in a revision must be:
   - relative, using `/` separators, with no leading `/` and no empty, `.`, or `..` segments
   - NFC-normalized, well-formed Unicode (no lone surrogates), with no control characters (C0, DEL, C1) and no backslashes
   - at most 512 bytes in UTF-8
   - not a case-only duplicate of another path in the same revision. Comparison is per segment, after NFC and `toLowerCase()`, so `Img/a.png` and `img/b.png` also conflict.
   - not using a file path as a directory: a file `a` and a path `a/b` can't coexist
   - not starting with the segment `r`. `r/` is reserved, because `/c/<id>/r/<rev>/…` is the pinned-revision URL.
5. **Fixed placement.** A revision's collection and parent never change.
6. **Parent before child.** A child revision is committed only after its parent has been committed.
7. **Revision limits.** A revision holds at most 2,000 files and 500 MB in total, and each blob is at most 50 MB. All three limits are configurable.

## Deletion

| Operation | Effect | Reversible | Needs cloud |
|---|---|---|---|
| **Soft delete** | Insert a `collection_tombstones` row. The collection is hidden from lists and the reader, and shown in the Trash view. | Yes: delete the tombstone row. | No; it syncs normally. |
| **Purge** | Permanently remove the collection and everything only it references. Runs as a resumable queued operation; see [write-path-and-sync.md](write-path-and-sync.md#purge). | No | Yes. It stays queued until it can finish. |

- **Individual revisions can't be deleted,** because that would break pinned URLs and share links.
- **Single-file redaction** (replacing a blob in an existing revision) is deferred.
- **Purge in phase 1 assumes a single writer.** Safe purge across multiple writers needs purge markers that survive sync, plus a grace period before blob garbage collection. That will be designed before a second writer is added; see the [roadmap](roadmap.md).

## Migrations

Turso Sync currently has open bugs: `RENAME`, `DROP COLUMN`, `RENAME COLUMN`, and `DROP` followed by `ADD COLUMN` corrupt or misplace data during sync. So:
- **Additive only.** Migrations add tables, nullable columns, and indexes. Nothing is renamed or dropped; to deprecate something, stop reading it.
- **Idempotent and automatic.** Migrations use `IF NOT EXISTS` and guarded `ADD COLUMN`, run at writer startup, and are recorded in `schema_migrations`.
- Prefer a new table over a new column on a heavily used table.
- **Rehearsed.** `apps/writer/tests/sync.test.ts` (needs `TURSODB_BIN`) runs the full migration set on one replica, pushes to a local `tursodb --sync-server`, bootstraps a second replica and migrates it again, so every new migration is checked for idempotence across replicas. A migration that alters an existing table should also be rehearsed against a replica that already holds data, as spike S4 did ([Turso Sync notes](turso-sync-notes.md#migration-rehearsal-s4)).
