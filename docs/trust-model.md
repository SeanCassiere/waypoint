# Trust model

This is the single source of truth for **who can do what** in Waypoint and **why**. Other docs link here instead of restating it. If you change anything listed here, update this page in the same PR and record the reason in [decisions.md](decisions.md).

## Zones

| Zone | Who is in it | Can read | Can write | Authenticated by |
|---|---|---|---|---|
| **Tailnet** | Any device on the owner's private network: with the Tailscale overlay, every device on their tailnet and the agents running on them; without it, the writer's own host (the writer listens on its loopback) | Everything, including deleted, pending, and failed items | Everything: create, revise, edit titles, delete, purge, create or revoke share links | Tailnet membership only. The writer has no login (D2). |
| **Public** | Anyone on the internet | Only what a valid, unrevoked, unexpired share link allows | **Nothing, ever** (D3) | Possession of a share token or derived revision capability |
| **Cloud providers** | Turso (metadata) and Cloudflare R2 (file contents) | Everything, at rest | Only through Waypoint's credentials | Provider accounts |

The tailnet is the trust boundary, not the home LAN. The writer is **not reachable from the plain LAN** (D37): LANs contain guests and IoT devices, and the writer has no auth. `deploy/compose.yaml` publishes it on the host's `127.0.0.1` only, and the Tailscale overlay publishes no host port at all. An operator who publishes it further (a LAN port, a reverse proxy without its own authentication) puts everyone who can reach it in this zone.

## The core rules

1. **IDs identify; they never authorize** (D4). Collection and revision IDs and public IDs end up in logs, screenshots, and chat. Knowing one never grants public access.
2. **Stored is not exposed** (D5). Turso and R2 hold *everything*, private content included. Public access exists only through share links.
3. **Deny by default in public.** The reader answers **404** for anything not explicitly allowed by a valid share link, with **one fixed page per route family**, byte-identical for every reason within the family: the raw-content family (`/x/…`) gets a small framable card (`frame-ancestors 'self'`) so a denial inside the shell's frame is readable, and everything else gets the full denial page. The family is visible in the URL the client requested, so the choice reveals nothing. It never returns 403, so it never confirms that something exists. The other non-denial URLs are the bare root `/` (a fixed 200 with no data, which has nothing to confirm) and the operational endpoints `/healthz`, `/healthz/deep` and `/robots.txt`. `/healthz/deep` counts toward the per-IP limiter, since it queries Turso and R2. The health endpoints reveal only the release version and deployed commit (`X-Waypoint-Version`, `X-Waypoint-Sha`), which are public in the repository anyway.
4. **The reader can't write, structurally:**
   - **Metadata:** its Turso token is created `--read-only`; writes return `BLOCKED`.
   - **Blobs:** it reads R2 over the S3 API with an **Object Read only** token scoped to one bucket. It has no R2 binding (D38).
   - **Code:** the Worker build contains no write routes.
   - **Logs:** access events go to Workers Analytics Engine, never the main DB (D26).
5. **The writer is the only path to the cloud** (D21 + phase-1 design). No machine writes to Turso or R2 directly.
6. **Agents can't destroy.** The MCP server exposes no delete, purge, title or metadata edit, or share-link creation. Those are owner actions in the writer UI or API. An agent may publish and revise, but publishing to the public is a human decision.

## Credentials: who holds what

| Credential | Power | Held by | Stored at |
|---|---|---|---|
| Turso full-access token (`waypoint-<env>`) | Read/write metadata | Writer | The writer env file in `~/.config/waypoint/` on the instance's host |
| R2 `waypoint-writer-<env>` | Read/write/delete objects in one bucket | Writer | same |
| Turso read-only token | Read metadata | Reader Worker | `reader-<env>.env` on the instance's host, then uploaded as a Worker secret |
| R2 `waypoint-reader-<env>` | Read and list one bucket | Reader Worker | same |
| Cloudflare deploy token (`waypoint-reader-deploy`) | Deploy Workers; edit DNS and routes on the reader's zone | `upgrade.sh` on the instance's host (run by hand or by the instance's ops runner) | `cloudflare.env` on the instance's host. **Never** a GitHub secret. |
| The deploy dispatch GitHub App's private key (optional) | Start, re-run or cancel the ops repository's deploy workflow, disable it, and delete its runs, logs and artifacts (Actions: write on that repository only) | Release workflow, `dispatch` job | The `release` environment secret `DEPLOY_APP_PRIVATE_KEY`, readable only by runs on `main` (D56) |
| GITHUB_TOKEN of the release workflow | Push to GHCR, attest, create the release and the release PR, attach the bundle to a release (one release-please created, or a maintainer did, for publish mode), approve the release PR's workflow runs (per job, least privilege) | `release.yml` jobs on `main` | Minted per run by GitHub |
| Tailscale auth key (for example tagged `tag:waypoint`) | Join the tailnet as the sidecar, once | Sidecar | `ts.env` on the instance's host; single-use, consumed at the node's first login |
| Share token key (`WAYPOINT_SHARE_TOKEN_KEY`) | Reproduce the working URL of every link whose ID it's combined with (D50) | Writer | The writer env file on the instance's host |
| Share tokens (`wps_…`) | Read one collection (or one revision) publicly | Whoever the owner shares the URL with, and the writer, which can re-derive them | Never stored. Only `sha256(token)` is, so a leaked database alone doesn't leak working links; the database plus the key does |

On the instance's host, all secrets are in `~/.config/waypoint/` (directory mode 700, files 600). They're passed to processes at runtime and never committed or baked into images. How to create or rotate them: [provisioning.md](provisioning.md).

## Share links

- **Format:** `https://<reader domain>/s/<token>/c/<collection public id>/…`. The token is `wps_` plus base64url(HMAC-SHA256(share token key, `"waypoint/share-token/v1\n"` + link ID)): 32 bytes that only a holder of the writer's key can produce (D50). The prefix makes leaked tokens easy for secret scanners to spot.
- **Recoverable, not stored:** the database keeps only `sha256(token)`, and the reader checks that hash. The writer re-derives a link's token from its ID whenever the owner asks for its URL, so the URL isn't a secret from the owner. A leaked database alone doesn't leak working URLs; the database plus the key does.
- **Rotating the key:** existing links keep working (the reader checks the stored hash), but the writer can no longer show their URLs (`url: null`); new links use the new key. If the key leaks, rotate it and revoke and recreate the links that matter. Links created before D50 used random tokens and never had a recoverable URL. The writer keeps no previous key, so the UI shows such links as "URL unavailable".
- **Scope:** one collection. A link either **follows the latest** revision or is **pinned** to one revision (D20). Viewers of a following link never see older revisions, since an older revision may contain something later removed.
- **Lifecycle:** created and revoked only on the tailnet. They can carry an expiry. Revocation takes effect within about 5 s of the writer's push, which starts immediately after the revoke (the reader caches live links for at most 5 s per isolate and never caches denials).
- **Tombstones win:** deleting a collection makes every link to it return 404. Undeleting reactivates links that were not revoked or expired; accepting a purge immediately revokes all its links.
- **What the holder sees about the link:** whether it follows the latest version or is a snapshot, and its own expiry (decision a). Never the link's label (the owner's private note), and no claim about logging.
- **Syncing note (RX-11):** holders of a Latest link learn that a newer revision is being synced and roughly when it started, but nothing about its content. Pinned links learn nothing.
- **Counts match the reader:** the writer's counts and filters use the reader's own liveness rule (revoked, expired, Trash, and the target revision having synced), written once in `shares.ts` in SQL and JS and tested against the reader.
- **Properties of a capability URL**, which the owner should understand:
  - Anyone holding the URL can view the content until it's revoked or expires.
  - URLs can end up in browser history, chat logs, and screenshots. Mitigations:
    - `Referrer-Policy: no-referrer` stops the token leaking to other sites.
    - `X-Robots-Tag: noindex` and a disallow-all `robots.txt` keep it out of search engines.
    - `Cache-Control: private` keeps shared caches from serving it after revocation.
    - Only denied protected requests count toward rate limiting. Once an IP exceeds 30 denials per 60 seconds, that reader isolate blocks it for 60 seconds before any DB or R2 access. Even valid links from that IP receive the same generic 404 during the block; this is acceptable because the block follows more than 30 denials. Blocked and ordinary denials have identical status, body, and headers.

## Untrusted content

Content is written by agents, so treat it as **untrusted HTML** wherever someone other than the owner might view it.

- **On the tailnet** (D23): agent HTML and markdown renditions are served from the writer's own origin without sandboxing. The owner trusts their own agents, and the convenience is worth it. Consequence: a malicious document opened in the tailnet viewer could call the writer API. The writer's CSRF checks (`Origin`/`Sec-Fetch-Site`, JSON-only) stop *other* websites, but not same-origin content. Revisit this if untrusted parties ever get tailnet access. Such content can also read working public share URLs (`GET /api/share-links`, D50). That's no new power: it could already create links.
- **In public**, content is sandboxed so a shared document can't act as the reader's origin:
  - Raw content responses carry `Content-Security-Policy: sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox allow-forms`, **without** `allow-same-origin`, so they run in an opaque origin.
  - The reader shell embeds content in `<iframe sandbox="allow-scripts allow-popups allow-popups-to-escape-sandbox">`.
  - Images are shown with `<img>` on the shell page, which never runs SVG script; the shell's `img-src` is the response's own capability prefix for its revision (decision c), so the shell can't load images from anywhere else.
  - The shell itself has a strict, hash-only CSP and runs no agent-supplied code. Its iframe URL contains a derived capability for only the resolved revision, never the full share token. Scripts in agent HTML can still read and exfiltrate the revision content they are shown, and may disclose that revision capability while it remains valid.
  - The shell's one script listens for the rendition's `waypoint:location` message. A document (or any page it navigates the frame to) can post anything, so the shell accepts only messages from the frame's own window, and only uses them to highlight a file it already links to and to replace its URL with that link's own href. The shell sends `Cross-Origin-Opener-Policy: same-origin`, so a popup a document opens (allowed to escape the sandbox) has no opener to navigate the shell with.
- **Markdown renditions** pass raw HTML through (they're agent content), so the same rules apply to them.

## Writer request safety (tailnet)

The writer trusts any client on the tailnet, but defends against *websites* attacking it through a tailnet user's browser:
- JSON endpoints require `Content-Type: application/json` (415 otherwise).
- Mutating requests from another origin are rejected with 403. The check is `Sec-Fetch-Site: cross-site`/`same-site`, or an `Origin` header that doesn't match the writer.
- Requests without browser headers (MCP, curl) pass.
- Viewer HTML pages send `Content-Security-Policy: frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN`, so another site can't frame them and trick a click on Revoke or Share. `/raw` (framed by the viewer itself) and the JSON API don't.
- GETs have no side effects but can be triggered cross-site (`<img src=…>`), so costly ones are bounded: diffs and Changes-page Markdown run under time budgets in a worker thread (D47).

## Code that runs on agent machines

The MCP launcher fetches `/mcp/server.mjs` from the writer and **executes it** (D36). The trust root is the writer, reached over **tailnet HTTPS**, and the bundle is checked against `X-Waypoint-Content-SHA256`. That check guards against truncation, not tampering: the writer itself is trusted. The launcher warns on stderr when `WAYPOINT_URL` is plain HTTP to a host other than loopback or `*.ts.net`, unless the operator sets `WAYPOINT_MCP_ALLOW_HTTP=1`, accepting that the bundle it then executes crosses that network unprotected.

## Deploy pipeline

- **Who can merge.** Only trusted maintainers have write access to this repository and can merge to `main`; branch protection requires `ci-ok`. Everything below rests on that: a merge to `main` is what a release is built from, and a release is what instances deploy (an accepted risk, below). Contributions from everyone else arrive as fork PRs.
- CI runs on GitHub-hosted runners. Its only credentials are for the Turborepo remote cache on Vercel (D52): the secrets `TURBO_TOKEN` and `TURBO_REMOTE_CACHE_SIGNATURE_KEY`, plus the repository variable `TURBO_TEAM`. They can read and write that cache and nothing of Waypoint's. Fork PRs get no secrets and run without the remote cache, and a first-time outside contributor's workflows wait for a maintainer's approval.
  - **Nothing deployed comes from the remote cache.** The writer image builds from source with turbo's caches off (the Dockerfile passes `--cache=local:,remote:`, and the image and install-test jobs get no cache credentials). `deploy/upgrade.sh` builds the reader and the packages it bundles with plain `pnpm --filter "@waypoint/reader..." build`, without turbo.
  - **The cache can only change CI's verdict.** turbo replays a cached result instead of running a check, so whoever holds both the token and the signing key could plant a passing result for a future task hash, and CI would skip that check. turbo rejects artifacts without a valid signature, so the token alone isn't enough. Same-repo PR runs get both, which is accepted because only maintainers can push branches here (see the accepted risks below). They're set for the whole workflow, and turbo passes every `TURBO_*` variable to its tasks even in strict env mode, so any step or test process of such a run can read them.
- **One deploy path** (D55). Every instance, the maintainer's included, deploys with `deploy/upgrade.sh` and its own `instance.env`. The instance file holds no secrets, only paths to mode-600 env files; it's parsed as literal `KEY=value` lines (never executed) and must be writable only by its owner, because it decides what runs. Secret values are never printed: reader secrets reach `wrangler secret bulk` through a mode-600 temporary file written just before the upload and deleted right after it (under Actions, in the runner's per-job temporary directory), and the Cloudflare token reaches Wrangler through its environment only. CI checks that no tracked file (and the release bundle builder that nothing in a bundle) names a particular instance's hosts, domains, machines or accounts (`scripts/check-owner-strings.sh`).
- **Instances deploy releases, not merges** (D58). Merging to `main` deploys nothing; nothing in this repository deploys at all. An instance runs `upgrade.sh <version>` (by hand, or from a private ops repository's workflow on a self-hosted runner on its host), which deploys only a release the release workflow built and attested (below). The maintainer's instance deploys this way too. (`upgrade.sh current-checkout` and `image` deploy what the operator built themselves, by hand, and trust it accordingly.) The runner, like any user that runs `upgrade.sh`, can read the instance's env files, and as a member of the `docker` group it is effectively root on its host. So:
  - Register a deploy runner only to a **private** ops repository whose one workflow runs released, attested code ([deploy/ops/deploy.yml.example](../deploy/ops/deploy.yml.example)), never to this repository or any repository that runs pull-request code.
  - **No self-hosted runner is attached to this repository**, and no workflow here may use one: CI's lint job parses every workflow as YAML and fails if any job's `runs-on` is anything but one GitHub-hosted label (from an explicit list, so an invented label shaped like GitHub's, such as `ubuntu-99.99`, fails), or a matrix value whose every value, spelled out in that job's own matrix, is one; `self-hosted` anywhere, label lists, runner groups, dynamic matrices, other expressions and reusable workflows of other repositories fail too (`scripts/check-hosted-runners.ts`). actionlint, which knows no custom label here, also fails on a custom label, though it accepts `self-hosted` itself. A self-hosted runner on a public repository that takes fork PRs could be made to run arbitrary code on its host.
  - **Never use `pull_request_target`** here: it would run with this repository's permissions for fork PRs.
- **Releases** (D56, [releasing.md](releasing.md)). `release.yml` runs on pushes to `main`, or by hand from `main` (`workflow_dispatch`, which needs write access; its `release-please` job refuses any other ref, so nothing publishes from a branch, and the `release` environment admits only `main` anyway, D60; with `publish_tag`, below, D61), on GitHub-hosted runners, with per-job least-privilege permissions, every action pinned by commit, and no `pull_request_target` or `workflow_run` trigger. release-please opens the release PR with GITHUB_TOKEN; merging it creates the release, and the same run builds the writer image natively per architecture (from source, no cache), merges a multi-arch index, builds the reader in a job with read-only permissions, and assembles the bundle in a job that runs no package code. The image's index digest and the bundle are attested (Sigstore-signed build provenance naming the workflow, commit, ref and runner). The bundle names the image digest, and the bundle builder refuses files that name the owner's instance.
  - **Publish mode publishes only a release commit of `main`** (D61). When a release's push run was missed and `main` has moved on, GITHUB_TOKEN can't create the release (it can't create a ref at an older commit once workflow files changed, which needs the `workflows` permission), so a maintainer creates the tag and release with their own login and starts `release.yml` from `main` with `publish_tag=vX.Y.Z`. Starting it needs write access to this repository (the same maintainers who can merge) or a token with `actions: write` on it; no workflow here passes it a tag. The `release-please` job then runs no release-please but `scripts/release-publish-check.sh`, from the run's own commit on `main`, so a branch can't change the check. It publishes nothing unless: the run is on `main`; the tag is `vX.Y.Z`; a published, non-draft, non-prerelease, mutable release exists for it and is the newest; the tag's commit (as GitHub resolves it, annotated tags peeled) is on the first-parent line of `main` at the run's commit, so it was merged to `main` (a release PR's branch head, a commit of a branch merged with a merge commit, or anything pushed only to a tag is refused); every version file at that commit says `X.Y.Z` and its first parent's didn't, so the tag can only name the one commit that released `X.Y.Z`, never a later commit of `main`; and the release has no bundle yet. The publishing jobs then run unchanged from that commit, which the job's outputs fix by SHA, so moving the tag afterwards changes nothing that's built. So whoever can start it can at most publish, once, the newest release commit that `main` already reviewed and release-please would have published; it can't publish arbitrary or unmerged code. The attestations name `release.yml` and `refs/heads/main` as for any release (their source commit is the head of `main` at the run, whose workflow and check did the building; the release commit is in the image's `WAYPOINT_BUILD_SHA` and the bundle's `BUILD_SHA`). `republish=true` lets the newest release be published again from the same commit (a new image digest under the same tags and a replaced bundle, both attested), for a release whose artifacts are unusable; it's refused for any older release, so the image's `latest` tag never moves back.
  - **The release PR's checks are approved by the release workflow** (D59). Because GITHUB_TOKEN opens and updates the release PR, GitHub holds its `pull_request` runs for approval by someone with write access, a safeguard against automation-written code running workflows that can read secrets unattended. The `release-pr-checks` job (`actions: write`, `pull-requests: read`) approves them through the API, so CI runs on the release PR without a click. That waives the safeguard for one branch only: it approves runs on the release PR's head commit, of `release-please--*` in this repository (never a fork's run, even on the same commit), on a branch that only release-please and people with write access can push, whose diff release-please derives from commits already reviewed on `main` (version strings and the changelog). If GitHub refuses the approval, nothing runs until a maintainer approves the runs on the PR, which they do when they review it to merge it anyway.
  - **Deploying a release verifies it first.** `upgrade.sh` (and the ops workflow, before running anything from a bundle) runs `gh attestation verify` with `--signer-workflow <repo>/.github/workflows/release.yml --source-ref refs/heads/main --deny-self-hosted-runners`, then pulls the image by the attested digest. A release built anywhere else (a branch, a fork, a self-hosted runner, another workflow) fails, and so does a tampered asset or registry tag. `VERIFY_ATTESTATIONS=0` opts out per instance.
  - **The dispatch carries nothing to trust.** After publishing, the `dispatch` job (environment `release`, `main` only) mints a short-lived token for the dispatching GitHub App, scoped to the ops repository and `actions: write`, and starts its deploy workflow with no inputs. The ops workflow resolves the latest release itself and verifies it; a `version` input is honoured only when its admin login started the run. A leaked App key can start or cancel deploys of the latest attested release, disable the deploy workflow (stopping automatic deploys until it's enabled again) and delete its run history, logs and artifacts; it can't read code or secrets, push, or pick a version, so it can't deploy anything but an attested release, and a cancelled deploy still finishes (it runs detached from its job, and its full log stays on the runner host, under `WAYPOINT_DEPLOY_WORK`). Forks without `DEPLOY_DISPATCH_REPO` skip the job.
  - **The ops runner** is registered only to the private ops repository, whose single workflow runs released, attested code, never pull-request code.
- **No reader is reachable except on its custom domain.** Each target's Wrangler config is generated with `workers_dev` and `preview_urls` off (unless a target sets `READER_<t>_WORKERS_DEV=true`), so there are no `workers.dev`, version or preview hostnames to protect. Custom domains stay public and production only.
- Dependencies: Dependabot alerts are triaged, and Dependabot's weekly, grouped version updates ([.github/dependabot.yml](../.github/dependabot.yml)) go through the full CI like any PR. Lockfiles are frozen in CI. pnpm's `minimumReleaseAge`, and a matching Dependabot cooldown, delay brand-new package versions. Workflow actions and base images are pinned by commit and digest.

## What's out of scope (accepted risks)

| Risk | Why it's accepted |
|---|---|
| A compromised tailnet device can read and modify everything | The tailnet is the trust boundary by design (D2). Protect it with Tailscale device approval and key expiry if that ever matters. |
| A leaked share URL grants access until revoked or expired | Capability-URL model. Revoke it in the writer; it takes effect within about 5 s of the writer's push. Passwords and audience grants are planned to narrow this. |
| Malicious agent HTML in the tailnet viewer can call the writer API | D23. The agents are the owner's own. |
| Turso or Cloudflare can read stored content | Accepted provider trust. There's no client-side encryption. |
| Anyone with merge rights to `main` can publish a release, and with it deploy every instance that follows releases automatically | A merge to `main` is what a release attests: the policy proves where a release was built, not that its code is good. Merging a release PR publishes the image and bundle that every instance verifies against, and (D56) dispatches the maintainer's deploy; instances that deploy on a schedule or by dispatch pick it up too. Accepted because merge rights are limited to trusted maintainers and branch protection requires `ci-ok`; reviewing what merges is the control. Adopters who want their own review step deploy by hand, or follow a fork. |
| A deploy runs with every credential of its instance, as a user that is effectively root on the host | `upgrade.sh` (by hand or from an ops runner) reads every env file the instance names, and the `docker` group is root-equivalent. Accepted because, run automatically, it runs only attested releases from `main` (above); `current-checkout` and `image` run only when the operator starts them. A persistent self-hosted runner could keep files, images or tool caches from one job for the next; the ops workflow uses a fresh work directory per run and pins its own `gh`. |
| Whoever holds the CI cache credentials can make a CI check pass without running it | D52. Same-repo PR runs get `TURBO_TOKEN` and `TURBO_REMOTE_CACHE_SIGNATURE_KEY`, so code pushed to a branch can plant signed cache entries that a later run on `main` replays instead of running that check. Deploys never use the cache, so this can hide a failing check but can't put cached code into production. Accepted because only maintainers can push branches here and fork PRs get no secrets. Rotate both secrets if either leaks. |
| Losing the R2 bucket loses content | The bucket is the durability floor; see [write-path-and-sync.md](write-path-and-sync.md#restore--disaster-recovery). |
